# Task 0001 — Establish the V1.1 evaluation set and cheap targeted reruns

> **Status: ✅ DONE** (implemented, 175 offline tests green, committed — see the V1.1 implementation commit)
>
> Implemented: `evaluation/v1_1_cases.json` (DET-001..004, OOV-001, COL-001..003, LAY-001/002, SIZE-001), `evaluate.py` (auto-scored detection with exact TP/FP/FN + human-review `color_review.md`, no automated color verdict), `selection.py` (`--only-panel` / `--force-characters` selectors), `--resume RUN --from-step STEP` copies only earlier-step outputs, targeted reruns reuse non-selected panels from the resume run so the page still stitches, forced ground-truth identities never make a paid call. Verified in `tests/test_evaluation.py` and `tests/test_orchestrator.py`.

## Goal

Create a small, fixed evaluation set from the real V1 failures and make it possible
to rerun only the relevant stages and panels. Character-identification quality and
colorization quality must be measured separately so a wrong VLM label is not scored
as a FLUX palette failure.

## Context

The first evaluation in [`pipelines.md`](../../pipelines.md) found both kinds of
failure:

- incorrect character assignments, including p003 panel 2 and p008 panel 3;
- correctly detected characters receiving wrong canonical colors, including
  Frieren's silver hair becoming magenta;
- a full-page illustration receiving no output because YOLO detected zero panels.

The current `--resume` behavior copies every completed stage, including colorized
outputs, and then skips stages that already have outputs. That makes controlled
prompt A/B tests awkward and encourages unnecessarily large reruns.

## Files

- `pipeline_v1/evaluation/v1_1_cases.json` — selected pages/panels, expected
  characters, failure category, and color-review expectations.
- `pipeline_v1/evaluate.py` — score detection precision/recall automatically and
  generate a human-review Markdown report for color outputs.
- `pipeline_v1/config.py`, `pipeline_v1/orchestrator.py` — targeted rerun and resume
  semantics.
- `pipeline_v1/tests/test_evaluation.py`,
  `pipeline_v1/tests/test_orchestrator.py`.

## Design

### Input aliases

Use source pages as the durable inputs; do not make the fixture depend on an ignored
historical `pipeline_v1/output/` directory. Panel IDs refer to the crops produced by
the existing reading-order extraction.

```text
VOL1_DIR = data/page_per_volume/Frieren - Beyond Journey's End v01 (2021) (Digital) (1r0n) (f2)
P003 = VOL1_DIR/Frieren - Beyond Journey's End - c001 (v01) - p003 [VIZ Media] [Digital] [1r0n].png
P004_005 = VOL1_DIR/Frieren - Beyond Journey's End - c001 (v01) - p004-p005 [VIZ Media] [Digital] [1r0n].png
P006 = VOL1_DIR/Frieren - Beyond Journey's End - c001 (v01) - p006 [VIZ Media] [Digital] [1r0n].png
P007 = VOL1_DIR/Frieren - Beyond Journey's End - c001 (v01) - p007 [VIZ Media] [Digital] [1r0n].png
P008 = VOL1_DIR/Frieren - Beyond Journey's End - c001 (v01) - p008 [VIZ Media] [Digital] [1r0n].png
CH134_004 = data/chapter_134/0134-004.png
```

Character arrays below are compared as sets; ordering is not significant.

### Character-detection failure cases

| ID | Input | V1 output | Expected output | Failure isolated |
|---|---|---|---|---|
| `DET-001` | `P003`, `panel_0002` | `{"characters":["Fern","Stark"]}` | `{"characters":["Frieren","Himmel"],"unknown_present":false}` | Present-day cast guessed inside a hero-party flashback crop. |
| `DET-002` | `P003`, `panel_0004` | `{"characters":["Sein"]}` | `{"characters":["Frieren","Himmel","Heiter","Eisen"],"unknown_present":false}` | Multi-character panel collapsed to one wrong priest. |
| `DET-003` | `P008`, `panel_0003` | `{"characters":["Sein"]}` | `{"characters":["Heiter"],"unknown_present":false}` | Heiter/Sein confusion in a close-up. |
| `DET-004` | `P008`, `panel_0004` | `{"characters":["Frieren","Sein"]}` | `{"characters":["Frieren","Heiter"],"unknown_present":false}` | One correct identity plus one confused identity. |
| `OOV-001` | `CH134_004`, `panel_0003` | `{"characters":["Sein"]}` | `{"characters":[],"unknown_present":true,"expected_unknown_characters":["Clematis"]}` | Clematis is outside the current 17-name reference vocabulary and must not be forced to the closest known priest. |

`unknown_present` is evaluation metadata, not permission for the detector to invent a
name. The `Clematis` identity is reviewed against the chapter dialogue and the
[chapter-134 plot/appearance order](https://frieren.fandom.com/wiki/Chapter_134).
Until the colorization reference set contains Clematis, the pipeline-facing
`characters` array remains empty and the reviewed name stays in evaluation metadata.

### Color-conditioning failure cases

These cases bypass paid character detection and inject the ground-truth identities.
Generated images are not compared pixel-for-pixel and the evaluator must not decide
whether a color case passes. It generates a Markdown report containing the image and
the expected output below; the user reviews the result visually.

| ID | Input and forced identities | Expected output |
|---|---|---|
| `COL-001` | `P003`, `panel_0006`; `Frieren` | Frieren has silver-white hair, green eyes where visible, and her white/gold canonical outfit; no magenta/purple hair; original text, linework, screentones, composition, and canvas size are preserved. |
| `COL-002` | `P007`, `panel_0006`; `Frieren` | Same canonical Frieren palette as `COL-001` despite a different crop and page; no magenta/purple hair; original text, linework, composition, and canvas size are preserved. |
| `COL-003` | `P008`, `panel_0003`; `Heiter` | Heiter has light green hair, glasses, and a black clerical robe with gold trim; he must not receive Sein's brown-hair/purple-blue outfit palette; original text and linework are preserved. |

The stored expected result for each color case has this machine-readable shape:

```json
{
  "characters": ["Frieren"],
  "required_colors": ["silver-white hair", "green eyes", "white/gold outfit"],
  "forbidden_colors": ["magenta or purple hair"],
  "preserve": ["text", "linework", "screentones", "composition", "canvas_size"]
}
```

### Color-review Markdown report

Write the report to the fresh run directory as
`<run>/evaluation/color_review.md`. All image links must be relative to the report so
the run directory remains portable. The report contains one section per generated
variant of every `COL-*` case and starts with run metadata: run ID, model/server,
prompt/profile hash, seed, FLUX settings, and generation time.

Required section format:

```markdown
## COL-001 — Frieren, p003 panel 6

- **Input:** `P003 / panel_0006`
- **Forced characters:** Frieren
- **Variant:** explicit-palette-v1

**Review status:** Pending user review

### Generated image

![COL-001 generated output](../../3_colorized/<page>/panel_0006.png)

### Expected output

- Frieren has silver-white hair and green eyes where visible.
- Her outfit uses the canonical white/gold palette.
- Her hair is not magenta or purple.
- Text, linework, screentones, composition, and canvas size are preserved.

### Review

- [ ] Pass
- [ ] Fail

Notes:
```

The generated image and expected-output text are mandatory. Also include smaller
links or previews for the monochrome input and exact atlas/reference used, because
they help diagnose a failure, but keep the generated image visually prominent. When
an experiment produces several prompt/profile variants, render each variant as its
own subsection with the same expected output and identify the variant explicitly.

The tool leaves every color result as `Pending user review`; only the user marks
`Pass` or `Fail` and adds notes. Do not infer a verdict with a VLM, color heuristic,
or another automated score in task 0001.

### Detection/geometry and cost failure cases

| ID | Input/configuration | Expected output |
|---|---|---|
| `LAY-001` | `P006` (1500×2250), full-page fallback enabled | Exactly one synthetic panel with box `[0,0,1500,2250]`, crop `panel_0001`, provenance `full-page-fallback`, followed by a stitched 1500×2250 colorized page. It must not be classified as blank. |
| `LAY-002` | Generated all-white 1500×2250 page, full-page fallback enabled | Zero panels, an explicit `blank-page` skip record, zero character/FLUX calls, and an unchanged 1500×2250 final page if stitching is requested. |
| `SIZE-001` | `P004_005` (3000×2250), detected panel box `[23,0,2918,2250]`, test cap `2.0 MP` | One panel remains one panel; FLUX request is 1600×1248 (multiples of 16, 1,996,800 pixels), while the final stitched page remains exactly 3000×2250. Record the original crop size, request size, scale, latency, and applied cap. |

If the final production megapixel cap differs from `2.0 MP`, keep `SIZE-001` as a
deterministic unit/evaluation configuration and add the selected production cap as a
separate measured case.

### Fixture schema

Every entry in `v1_1_cases.json` must include an explicit input and expected output;
free-form prose alone is insufficient. For example:

```json
{
  "id": "DET-003",
  "stage": "characters",
  "input": {"source_page": "P008", "panel": "panel_0003"},
  "expected": {"characters": ["Heiter"], "unknown_present": false},
  "baseline": {"characters": ["Sein"]},
  "failure": "known-character-confusion"
}
```

Add a panel selector such as repeated `--only-panel PAGE_STEM:PANEL_STEM`. Change
`--resume RUN --from-step STEP` to copy only the outputs before `STEP`; later-stage
outputs must not be copied into the fresh run. Every targeted run still gets its own
timestamped directory and complete manifest.

Record, per case:

- expected and detected canonical characters;
- identity true positives, false positives, and false negatives;
- for color cases, the generated-image path, the expected-output text copied from
  the fixture, and a `Pending user review` status in the Markdown report;
- seed, prompt/profile version, latency, calls, and measured API cost.

## Tests

- Every case has resolvable inputs (or an explicit generated-input recipe) and a
  schema-valid expected output.
- `DET-*` compares character arrays without depending on response order and reports
  exact false positives/negatives.
- `COL-*` runs with forced ground-truth identities and never makes a paid detection
  call.
- The color-review report includes every generated `COL-*` variant, embeds its
  generated image with a valid relative path, reproduces the fixture's expected
  output without drift, and defaults to `Pending user review`.
- No code path automatically changes a color case to pass or fail.
- `LAY-*` and `SIZE-*` assert the exact geometry and call counts above.
- Evaluation calculations distinguish detection errors from colorization errors.
- A targeted rerun processes only selected panels while stitching the correct page.
- `--resume ... --from-step colorize` reuses panels/characters but regenerates
  colorize/stitch outputs in a fresh run.
- Existing full-run and mock behavior remains unchanged.

## Acceptance criteria

- [ ] The fixed case file contains the exact inputs and expected outputs listed above.
- [ ] Each supported failure category has at least one regression case: character
      confusion, out-of-vocabulary identity, palette adherence, zero-panel fallback,
      blank-page skip, and oversized-input capping.
- [ ] A prompt experiment can rerun only the selected panels without paid character
      calls when ground-truth identities are requested.
- [ ] Detection results are scored automatically against their exact expected sets.
- [ ] Color results produce `<run>/evaluation/color_review.md` with each generated
      image, its expected output, input/reference context, and empty Pass/Fail
      checkboxes for user review.
- [ ] The evaluator does not assign color pass/fail results automatically.
- [ ] Tests pass and the behavior is documented in `pipeline_v1/README.md`.
- [ ] Commit with a meaningful message.
